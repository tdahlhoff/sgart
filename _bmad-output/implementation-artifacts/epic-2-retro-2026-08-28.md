## 2. What Went Well

1. **The premature-value story-authoring rule (Epic 1 Action 4) worked.** Every story's
   Clarifications section explicitly named and deferred out-of-scope surfaces with a reason
   (store prefill deferred 2.5→2.6, DONE-rejects-item e2e deferred to Epic 3, clear-to-unassigned
   deferred post-MVP) instead of over-building or silently skipping them. This discipline held
   for all 6 stories.
2. **The command-id abstraction (Epic 1 Action 1) worked.** The dominant Epic 1 bug class
   (duplicate households, silent no-op renames, vanished stores) **did not recur** in Epic 2 —
   no story's review findings mention a commandId dedup defect, despite Epic 2 being "nothing but
   rapid list/item writes" exactly as Epic 1's retro predicted.
3. **The one real end-to-end stack run (Epic 1 Action 6) paid for itself immediately** — it
   surfaced a missing `spring-boot-flyway` dependency that had silently disabled Flyway since
   Story 1.6, an invisible defect no Testcontainers/unit test would have caught.
4. **The first process manager (Story 2.4) landed cleanly and was hardened by review**: a real
   `ConcurrencyConflictException`-swallow bug (moved item stranded on neither list) was caught
   and fixed with a retry-on-conflict fix before merge — validates the PM pattern for reuse in
   Epic 3's trip-completion transfer.
5. **The reusable store picker (UX-DR22, Story 2.6) shipped as a genuine component**, not a
   one-off screen — Story 2.6's dev notes already scope how Story 3.1 extends it to multi-select,
   so Epic 3 inherits a tested building block instead of starting from scratch.

## 3. What Repeated — Challenges

### 3.1 Optimistic client-state drift after multi-step flows — the dominant Epic 2 bug class
Every multi-step or cross-object client flow produced at least one review-caught divergence
between what the server actually did and what the optimistic UI showed:

- **2.4** — the merge dialog's pre-filled quantity used grouped thousands formatting
  (`"1.600"`), and the un-group step was missing, so any merge summing ≥ 1000 silently wrote
  ~1000× too little to the target (data corruption, not just a stale read).
- **2.5** — `unfocus()` after every fast-add cost the keyboard on every single article; the
  suggestion cache was replaced wholesale on refetch, clobbering an in-flight optimistic add.
- **2.6** — an inline-created store wasn't merged into `state.stores`, so a just-assigned item
  showed the "+ Geschäft" ghost chip as if the assign had failed; editing an assigned item
  optimistically dropped its `storeId`, wiping the chip until reload — a client-side echo of the
  very regression trap (Cl. 7) the backend was carefully guarded against.

None of these were caught by dev; all were caught by review. **Decision (Timo, 2026-08-28):**
add "optimistic client state reflects every server-visible side effect of the action, including
inline-created objects and preserved fields from prior commands" to the story DoD, checked
explicitly during implementation — see Action 1.

### 3.2 Concurrent-tap / re-entrancy guards still inconsistent
`removeItem` shipped without the `isSubmitting` guard its siblings had (2.3); the move-target
sheet had no re-entrancy guard across an awaited collision read and could pop a context twice
(2.4); a shared `_removeIntent` lost its idempotent-retry id under concurrent removes (2.3).
Same class of bug as Epic 1's §3.1 commandId footgun, one layer up — the fix pattern
(`isSubmitting` gate + per-row `CommandIntent`) is known but not yet applied uniformly on
first pass.

### 3.3 Base error-advice contract test and extended DoD (Epic 1 Actions 2/3) did not land
Neither shows up as built in any Epic 2 story. The symptoms Action 3 was meant to front-load —
missing a11y labels, dead code, stale doc comments — still surfaced in review rather than dev
(Story 2.5: no a11y semantics on the fast-add field despite Task 11 claiming it done; the
`item_form_sheet` add-mode branch was dead code after the fast-add field replaced it). **Decision
(Timo, 2026-08-28):** carry both forward into Epic 3, explicitly scoped to Epic 3's first story —
see Action 2.

### 3.4 Read-model isolation and reprojection edge cases keep needing a second pass
2.1's `DO UPDATE` vs `DO NOTHING` rename-reversion bug, and untested cross-household isolation
(2.1, 2.3) both needed a review round to catch. Pattern: a new read model's replay/isolation
behavior is not exercised until review asks for the two-household / replay-order test explicitly.

### 3.5 Process felt lighter than Epic 1, as the root-cause fixes predicted
Epic 1's retro predicted that fixing the commandId root cause and adopting the premature-value
rule would lighten the per-story loop. Epic 2's review counts (4 decision-needed across 6
stories, only 2.4 and 2.5 needed a Timo decision) bear that out — no story needed the kind of
HIGH-severity "read path never activates" defect Epic 1 saw in 1.6.

## 5. Next Epic Preview — Epic 3: Shopping Trips & Print

Five stories: start a trip across selected stores · store-grouped trip view with
assignment/rerouting · check-off/uncheck/postpone during a trip · complete a trip with leftover
review · print and share the list.

**Dependencies on Epic 2 — all present and stable:**
- `Item`/`ShoppingList` aggregate and read models (2.3–2.6) — trips read and mutate the same
  items.
- The reusable store picker (2.6, UX-DR22) — Story 3.1 extends it to multi-select per its own
  dev notes (Cl. 8); no rebuild needed.
- The process-manager pattern (2.4) — Story 3.4's leftover-transfer and 3.3's postpone-to-list
  both need the same idempotent cross-aggregate-add shape; the 2.4 concurrency-conflict-retry
  fix should be applied from the start this time, not caught in review again.
- Command/concurrency envelope (1.5) and commandId abstraction (Epic 1 Action 1) — no new work
  needed.

**New work / risks to plan for:**
- **`ShoppingTrip` — a new aggregate, Epic 3's first.** First real test of whether the
  Household/ShoppingList aggregate patterns generalize to a third aggregate type.
- **Print/PDF generation and the native OS print dialog** — genuinely new technical territory,
  no Epic 1/2 precedent; Story 3.5's "no PDF persisted to device storage" constraint needs an
  in-memory-only PDF library choice made deliberately, not discovered mid-story.
- **The cached Done-archive invalidation gap (deferred from 2.2)** becomes reachable the moment
  Story 3.4 produces a real Done list — the fix (reset `archiveStatus` to `idle` on a Done
  transition) needs to land in or before 3.4, not be rediscovered in review.
- Optimistic-state discipline (Action 1 below) matters more here than in Epic 2: trip
  store-grouping, rerouting, and the leftover-review dialog are all multi-step client flows of
  exactly the shape that caused 3.1's predecessor bugs.

**Readiness verdict:** Epic 3 is clear to start. Test suites (backend 415 / Flutter 418, all
green) plus the one real stack run give sufficient confidence for a pre-beta, no-stakeholders-yet
project (Timo's call, 2026-08-28) — no separate manual QA pass required before starting. No
significant discovery from Epic 2 requires an Epic 3 replan.

## 6. Action Items (carried into Epic 3)

1. **Add an explicit optimistic-state DoD check.** For any client action with a side effect
   beyond the item being edited (inline-created objects, preserved fields carried through an
   unrelated update, focus/keyboard state across a submit), the story's implementation — not its
   review — must verify the optimistic rebuild reflects every server-visible effect.
   *Owner: Dev · From Epic 3's first story · Directly targets §3.1, the dominant Epic 2 bug class.*

2. **Re-commit to Epic 1 Actions 2 and 3, explicitly scoped to Epic 3's first story.** Build the
   base error-advice contract test (every command endpoint maps bad input/domain exceptions to a
   4xx) and treat the extended DoD (a11y labels, no dead code/strings, fail-fast guards) as a
   pre-review checklist item, not a review-time discovery.
   *Owner: Dev · From Epic 3 story 1 · Targets §3.3.*

3. **Apply the `isSubmitting`/re-entrancy guard pattern uniformly on first pass**, not per-story
   rediscovery — every client command handler on a row/dialog gets the guard by default,
   mirroring the already-proven `addItem`/`updateItem` shape.
   *Owner: Dev · From Epic 3's first write path · Targets §3.2.*

4. **New read models get an isolation + replay test in the same PR that introduces them**, not
   added in review — two-household isolation and a replay-order/idempotency assertion are now a
   known-needed pair for any new projector case.
   *Owner: Dev · From Epic 3's first new read model (trip read model) · Targets §3.4.*

5. **Fix the cached Done-archive invalidation gap (deferred from 2.2) proactively** when Story
   3.4 introduces the first real Done transition, rather than waiting for review to rediscover
   it.
   *Owner: Dev · Story 3.4 · Already logged in `deferred-work.md`.*

6. **Apply the 2.4 process-manager concurrency-conflict-retry fix from the start** in Epic 3's
   new PMs (postpone-to-list, leftover-transfer) — the fix is known (retry on
   `ConcurrencyConflictException`, re-derive the same commandId), don't let review rediscover it.
   *Owner: Dev · Stories 3.3/3.4.*

## 7. Technical Debt Carried Forward (from `deferred-work.md`, Epic-2 additions)

**Reachable in Epic 3 — fold into the relevant story:**
- Cached Done-archive invalidation (→ Action 5, Story 3.4).
- Process-manager `DuplicateItemException` swallow discarding a moved item's quantity in a rare
  race (→ Epic 3's mid-move compensation work, if built).
- PM subscription never cancels its KurrentDB `Subscription` handle on `stop()` (shared with the
  projector's identical leak — fix both together).

**Deferred to Epic 6 (erasure/retention):**
- `item_read_model` / `item_suggestion_read_model` have no FK/`ON DELETE` cascade to
  list/household.
- Unbounded, unpruned `item_suggestion_read_model` growth (post-MVP: member-facing "remove from
  suggestions" action, doubling as item-level erasure).

**Latent / cosmetic / no current trigger:**
- `MoveItemRequest` and sibling write DTOs have no `@Valid`/null-body guard (500 instead of 400
  on an empty body) — harden `ItemController` as a group when next touched.
- No shared transaction across a projector event's multiple read-model writes (pre-existing since
  2.1).
- `normalized_name VARCHAR(120)` can be exceeded by Unicode-lowercasing a 120-char name (vanishingly
  rare for German grocery content).
- Suggestion-panel is an inline layout shrink, not a floating overlay (functionally meets the AC).
