## 2. What Went Well

1. **The aggregate patterns generalized to a third aggregate type.** Epic 2's retro flagged
   `ShoppingTrip` as the open risk — "first real test of whether the Household/ShoppingList
   patterns generalize." They held: two process managers, a two-phase saga, two projectors, and
   the hexagonal + AD-3/AD-10 (reference-by-id, cross-aggregate-via-PM) rules never bent.
   `HexagonalArchitectureTest` passed unchanged across the whole epic.

2. **The correct-course discipline worked as designed.** The 3.3 review found a genuine design
   flaw — the cross-aggregate transfer could silently drop an item if the target left `OPEN`
   mid-flight. Rather than bodge an in-line fix, it was correctly triaged as too structural,
   formally carved into its own planned story (3.6) via a sprint-change-proposal, and shipped as a
   proper reserve-then-remove compensating saga. Process caught the problem *and* right-sized the
   response.

3. **New technical territory (print/PDF, 3.5) landed cleanly and deliberately.** The "no PDF
   persisted to device storage" constraint was enforced **structurally** — `package:printing`
   confined to one seam, no `path_provider`/`File`/`dart:io` anywhere under `features/lists/print/`
   (grep-verified) — not merely asserted in a test. The in-memory PDF library choice was made
   up front, not discovered mid-story, exactly as the Epic 2 retro asked.

4. **Two Epic-1 root-cause fixes still hold, three epics on.** No commandId dedup defect and no
   premature-value over-build appeared anywhere in Epic 3. The fixes that *changed the code once*
   have never regressed.

5. **Dependency currency is genuinely maintained (§7).** Spring Boot 4.1, Gradle 9.7.1, Flutter
   3.12, current CI action majors — no deprecated pins accrued during the epic. Story 3.5 confirmed
   `printing`/`pdf` were the current stable majors before adding them.

## 3. What Repeated — Challenges

### 3.1 The item-transfer / status model churned three times (Timo's diagnosis — the headline)

The single biggest lesson, and Timo named it unprompted: the confusion around moving an item out
of a trip to another list vs. flagging it "postponed / do-not-buy" **could have been prevented by
planning that part of the model up front when drafting the epic.** The record bears it out — the
same shared model was reworked in three consecutive stories:

- **3.3** introduced `ItemStatus {OPEN, DONE, POSTPONED}`, all three postpone variants, and a
  separate `ItemPostponedToList` move. Review nearly *deleted* in-place POSTPONED as valueless
  before its purpose was recognized mid-review.
- **3.4** *retired* in-place POSTPONED entirely, replacing it with a terminal `DISCARDED` /
  `ItemDiscarded`.
- **3.6** *unified* move + postpone into one `ItemTransferInitiated/Confirmed/Cancelled`
  vocabulary — retiring `ItemMovedToList` (2.4) and `ItemPostponedToList` (3.3), both just built.

We shipped and then deleted three transfer/status events inside one epic. It was cheap **only**
because nothing is deployed and the event store can be reset freely — in Epic 4 (beta), that churn
would cost a migration + codec-tolerance pass each time. **Root cause is a planning one:** the
Epic-3 ACs described behaviors ("postpone to a list", "flag in place", "discard on completion")
but no one drew the **item lifecycle state machine** or fixed a **single ubiquitous transfer
vocabulary** across trips *and* lists before Story 3.3, so each story discovered the model the
previous one got slightly wrong. → **Action 1.**

### 3.2 Dominant defect: tasks marked `[x]`, tests absent

The recurring Epic-3 review finding was not a missing edge case — it was the task checkbox not
meaning what it says.

- **3.3**: Tasks 7/8/9/12/14/22 all marked done with **zero** coverage behind them (three handler
  tests, the PM's postpone-to-list path incl. the target-not-Open drop, all four new endpoints).
- **3.4**: `renameADoneList_throws`, `uncheckItem_returnsADiscardedItemToOpen`,
  `completeTrip_onADoneList_throws`, the discard handler test, and the projector
  membership + two-household isolation/replay tests — all specified, all `[x]`, all absent until
  review caught them.

This is an integrity gap, and it directly defeated Epic 2's Action 4 ("new read models get an
isolation + replay test in the same PR") — in 3.4 those were among the absent tests. → **Action 2.**

### 3.3 Optimistic client-state drift (Epic 2's dominant class) still recurring

Epic 2's Action 1 added a DoD check for exactly this; it still slipped three times:
- **3.1** — `startTrip` reverted the list to an editable Open view on a 409 over an
  already-In-Trip list (every follow-up edit would then 409).
- **3.2** — reroute after a failed trip-side add stranded the item as unassigned and wiped the
  add-store error.
- **3.4** — the completion sheet was a frozen `cubit.state` snapshot: "Verwerfen" gave no feedback,
  "N von M" never updated, and confirm could silently no-op while a discard was in flight.

### 3.4 Second-pass-review quality: the fix-up pass itself needs rigor

The two second passes (3.3, 3.4) found real defects *in the first pass's fixes*:
- **3.4** — the bounded-retry fix (itself an Epic-2 Action-6 item) shipped with a **hollow test**
  that appended the conflicting event before the PM read, so the retry/catch branch was never
  exercised; the assertion passed for a single-shot append.
- Fixes introduced **fresh javadoc/code contradictions** (the same commit that purged stale
  `POSTPONED` docs left `completeTrip`'s "raises on DONE" doc contradicting its new convergent
  no-op behavior). → **Action 4.**

### 3.5 Meta-pattern: which actions held, and which decayed

Two root-cause fixes from Epic 1 (commandId, premature-value) held for three epics. But three of
Epic 2's six actions came back **partial**. The pattern in the pattern:

> **The actions that changed the code once held. The actions that asked the dev loop to remember
> something every story decayed.**

This is the strategic insight for Epic 4's action design — prefer structural / code-once
enforcement over per-story reminders. Timo's choice of an automated task↔test manifest diff
(Action 2) over a "verify-before-check" habit is exactly this instinct applied. → **Action 3.**

## 5. Next Epic Preview — Epic 4: Live Collaboration & Membership 🚩 Beta milestone

Six stories: invite by email · accept & join · roles & governance · **real-time live sync** ·
content-free notifications · invite-acceptance web fallback. This is the shared, live
differentiator — Epics 1–3 were the solo-capable substrate.

**Dependencies on Epic 3 — present and stable:** the trip lifecycle, the PM + compensating-saga
patterns, and every read model/projector we built.

**New work / risks to plan for:**
- **First GDPR-touching PII feature.** HMAC email pseudonymization (AD-6), raw email only in a
  purge-on-accept side-store, the last-Admin invariant, household deletion. CLAUDE.md §5 (DSGVO)
  moves from *designed-but-unexercised* to *must-be-exercised* — and §6 requires the privacy
  guarantees (no raw email persisted, purge-on-accept/expiry/erasure) to have **their own
  first-class tests**, not be inferred.
- **SSE live sync replaces the optimistic model.** Every Epic 1–3 "actor sees their own change,
  peers refetch on open" assumption is superseded by 4.4. The many "peers refetch on open" deferrals
  across 3.2/3.3 become real requirements.
- **Two Epic-3 deferrals get teeth under multi-user live sync:**
  - The `fromStart`-replay-on-every-reconnect projectors (3.2, 3.6) — O(all events) per resubscribe —
    become a real cost once SSE clients reconnect constantly. Checkpointed subscriptions are the fix.
  - The cross-projector transient (`GET /active` briefly returning a trip with an empty store set)
    stops being "the actor sees it for a second" and becomes "every connected member sees it live."
- **Process switch at beta:** git workflow moves from commit-to-main to branch + PR (per the
  standing beta plan).

**Readiness verdict:** Epic 4 is clear to start. Test suites (backend 656 / Flutter 513, all green)
give sufficient confidence for a pre-beta project. **No significant discovery from Epic 3 forces an
Epic 4 replan** — the plan already anticipates the optimistic→live-sync shift. The items above are
readiness/debt notes to fold into planning, not a replan.

## 6. Action Items (carried into Epic 4)

1. **Model-first planning for shared state.** When an epic touches a shared state model or a
   cross-aggregate vocabulary, draft the **state machine + the single ubiquitous transfer
   vocabulary** as an explicit up-front artifact during epic / first-story planning — before the
   first story that mutates it. Directly targets §3.1, the epic's headline lesson (Timo's
   diagnosis).
   *Owner: PM + Architect · During Epic 4 planning, and specifically before the membership/role
   state model in 4.1–4.3.*

2. **Automated task↔test cross-check (structural, not a reminder).** `create-story` emits an
   expected-tests manifest (task → named test); a check script (or a code-review pre-step) diffs
   claimed-done `[x]` tasks against tests that actually exist and **fails the story** if a `[x]`
   task has no matching test. Targets §3.2, the dominant Epic-3 defect. *Chosen by Timo over a
   per-story "verify-before-check" habit precisely because code-once enforcement survives and
   reminders decay (§3.5).*
   *Owner: Dev + Process · From Epic 4's first story.*

3. **Prefer structural / code-once enforcement over per-story reminders for recurring DoD items.**
   Rather than re-committing the optimistic-state check (Epic 2 Action 1) and read-model
   isolation+replay (Epic 2 Action 4) as memory items a *fourth* time, fold them into
   `create-story` scaffolding / the manifest of Action 2 where possible. Targets §3.3 and the §3.5
   meta-pattern.
   *Owner: Process · Epic 4 planning.*

4. **Fix commits get first-pass rigor.** A fix's test must exercise the exact branch it claims
   (no hollow retry tests, per §3.4), and a fix must not leave contradicting javadoc/docs behind.
   Treat every second-pass fix commit as reviewable code, not a rubber-stamp.
   *Owner: Dev · Every review-fix commit in Epic 4.*

5. **Build the base error-advice contract test — or formally retire the action.** This is the
   third epic carrying Epic 1 Action 2 unbuilt, while distributed per-endpoint coverage has
   actually held up. Decide, don't drift: either build the standalone contract test in Epic 4's
   first endpoint story, or consciously retire it as superseded by the per-endpoint pattern.
   *Owner: Dev + Timo decision · Epic 4's first endpoint story.*

6. **Address the checkpointed-subscription debt before/early in live sync (4.4).** The
   `fromStart`-replay-on-every-reconnect projectors and the cross-projector empty-store-set
   transient both become multi-user-visible under SSE. Evaluate checkpointed subscriptions and a
   client "trip still loading" settle affordance during 4.4 planning, not mid-story.
   *Owner: Architect + Dev · Story 4.4.*

## 7. Technical Debt Carried Forward (from `deferred-work.md`, Epic-3 additions)

**Gets teeth in Epic 4 (see Action 6):**
- `fromStart` replay on every projector restart/resubscribe — repo-wide, no checkpoint (3.2, 3.6).
- Cross-projector transient: `GET /active` can briefly return a trip with an empty store set (3.2).

**Accepted-with-note (rare, mirrors the accepted `TripLifecycleProcessManager` pattern):**
- Retry-exhaustion strands a reserved item fail-fast-locked until the next restart (3.6) — 5
  consecutive same-stream conflicts in a household grocery app is vanishingly unlikely.
- Post-confirm lost-response retry returns 404 not a convergent success; self-heals on next
  refresh. Fully closing it needs source-side tombstones (3.6).
- Same-target retry after the target leaves OPEN 409s instead of converging; eventual state is
  consistent (3.6).

**Latent / cosmetic:**
- Empty-string note prints a dangling " · " separator (3.5) — byte-identical to on-screen; fix
  belongs to both call sites, hinges on whether the server can deliver a non-null empty note.
- `TripCompletedForList` fold sets `status=DONE` but never clears `activeTripId` (write vs read
  model disagree; harmless while DONE lists are immutable) (3.4).
- Add-store endpoint ignores the `{listId}` path segment; membership is the real gate (3.2).

**Deferred to Epic 6 (erasure/retention):**
- `item_read_model` / `item_suggestion_read_model` have no FK/`ON DELETE` cascade.
- Unbounded, unpruned `item_suggestion_read_model` growth.
