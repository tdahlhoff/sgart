- (decision) Input is rich + pre-sorted (PRD authoritative for capabilities, architecture spine = build contract, addendum + SGART.md = prior design, CLAUDE.md = project conventions). Mode: direct extraction, no elicitation. Create op.
- (note) WHY: vision-to-realize + opportunity. Replace the paper list / whiteboard / 'add milk' WhatsApp with ONE shared, live household shopping list that stays correct in-aisle; longer-term, turn every confirmed purchase into a private household record of what things cost where. Privacy is a first-class product property (self-hosted German, no US cloud), not compliance afterthought. MVP launches to a friends-&-family cohort. Solo household is a first-class case.
- (capability) CAP-1 Households & first-run routing. intent: an authenticated person with no household can create one (becoming its first Admin) or wait for an invite, and is routed correctly on launch by how many households they belong to. success: after create, creator is a Member with role Admin; zero households -> create/await-invite choice, one -> straight in, several -> selection screen. (PRD FR-1)
- (capability) CAP-2 Invite & membership lifecycle with roles. intent: any Member can invite a person by email; the invitee authenticates via the link and joins; roles (Admin/Participant) gate only governance actions while both do all daily work. success: 2nd pending invite to same email rejected; expired invite unredeemable; accept adds Member with role Participant; last Admin cannot leave/be demoted; only Admin removes others, promotes, or deletes household. (PRD FR-2, FR-3)
- (capability) CAP-3 Store management with client-side chain matching. intent: any Member can add/remove household Stores by free-form name, with an advisory StoreChain suggestion matched client-side as they type. success: store name unique per household (dup rejected); chain link optional and user-confirmed (accept/change/clear); chain reference list works offline after first cached load. (PRD FR-4, FR-5)
- (capability) CAP-4 Multiple shopping lists with optional auto-naming. intent: a household can hold several Open lists at once, each with an optional name. success: >1 Open list allowed; unnamed lists display 'Liste {N}' by creation order among Open/In-Trip lists (derived, not stored); name settable anytime except when Done. (PRD FR-6)
- (capability) CAP-5 Item management & off-trip status transitions. intent: any Member can add/update/remove items (name, quantity, unit, optional note) and check/uncheck/postpone them on an Open list. success: quantity>0; exact name+note duplicate on same list rejected; check->Done, uncheck->Open; postpone targets an existing list, a new list, or flags in place; a Done list accepts no item commands. (PRD FR-7, FR-8)
- (capability) CAP-6 Fast item entry with autocomplete & attribute prefill. intent: as a Member types an item name, the app autocompletes from the household's own past item names and prefills typical attributes (unit, note, default store) for near-zero-tap entry. success: suggestions are prefix/fuzzy, household-scoped/private, lag-free from a local/cached lookup; selecting one prefills last-used attributes (overridable); a brand-new name adds with no extra steps. (PRD FR-27)
- (capability) CAP-7 Real-time live sync. intent: changes to lists, items and trips propagate to all connected household Members' devices in near-real-time without manual refresh. success: a change by one Member appears on another's device within a few seconds under normal connectivity; the client auto-reconnects and reconciles state after a drop. (PRD FR-10)
- (capability) CAP-8 Offline queue with bounded conflict surfacing. intent: actions taken offline are captured locally, replayed in order on reconnect with a visible pending count, and genuine conflicts are surfaced for a coarse keep/discard choice rather than silently overwritten or auto-merged. success: offline check/uncheck/add succeed locally and show pending; replay is idempotent (no double-apply on retry); a queued command whose target aggregate advanced is rejected and the Member gets an inline re-apply/discard choice; convergent actions resolve silently. (PRD FR-11, FR-26)
- (capability) CAP-9 Shopping trips: start, store-grouped view, routing & in-trip actions. intent: a Member can start a Trip from an Open list across one or more selected Stores, see items grouped by Store (with a 'Not yet assigned' section), assign/reroute items between stores (incl. spontaneously added stores), and check/uncheck/postpone during the trip. success: trip requires a linked list + >=1 store and moves the list to In-Trip; at most one Active trip per list; unassigned items show under 'Not yet assigned'; reroute moves an item to any store in the trip; in-trip check/uncheck/postpone sync live. (PRD FR-12, FR-13, FR-14)
- (capability) CAP-10 Complete a trip with leftover review. intent: trip completion is a guided, user-triggered dialog that reviews remaining open items and closes the trip. success: dialog confirms 'finished?', then per open item offers TRANSFER (to an existing or new list) or DISCARD; TRANSFER places items automatically; on completion the list moves to Done and becomes immutable; the system never force-completes a trip. (PRD FR-16)
- (capability) CAP-11 Print & share the list. intent: a Member can print the current list via the native OS print dialog in the grouped-by-store layout, and secondarily share it as an in-memory PDF. success: printout groups items by store with a 'Not yet assigned' section matching the on-screen layout; no PDF is persisted to device storage in either path. (PRD FR-17, FR-18)
- (capability) CAP-12 Content-free notifications. intent: the system keeps Members coordinated via push pings that carry no household data and only prompt the app to fetch real state from the household's own server, on a fixed MVP default set. success: push payloads contain no item/list/receipt content; defaults = invitation received (always on), list changed (debounced ~5min, at most one ping per list per interval), trip started/completed. (PRD FR-19)
- (capability) CAP-13 German-first, internationalization-ready UI with locale selection. intent: the MVP ships a complete German UI with all user-facing text and formatting locale-driven (not hard-coded), and a Member can view/change their own Locale in-app. success: no untranslated strings in primary flows; no hard-coded user-facing strings (all via localization layer); currency/date/number formatting follows active Locale (de-DE renders '1,09 €'); changing Locale updates language+formatting without reinstall; Locale is per-user, device-default then fallback de-DE. (PRD FR-24, FR-25)
- (capability) CAP-14 Data-subject rights: erasure & export. intent: a person's personal data can be located, exported, and erased on request, honoring DSGVO right-to-erasure and portability despite an immutable event log. success: erasure destroys the Identity-ACL mapping + scrubs read models/caches + deletes the Keycloak account, leaving only unlinkable pseudonyms in the log (no personal data recoverable); a person's data can be exported in a portable form; explicit tests cover erasure, export, and retention. (CLAUDE.md §5, PRD §8.1 resolved by ARCHITECTURE-SPINE AD-5/6/7)
- (constraint) No US cloud dependency, ever: self-hosted on a dedicated German/EU server, no US hyperscaler in the data path. Bends hosting, provider, push, OCR, and geodata choices. (PRD §5)
- (constraint) DSGVO by design: personal data minimized; events carry NO personal data (household-scoped pseudonymous MemberId only, never keycloakUserId/email/name); push payloads content-free; erasure by de-linking without rewriting history. Bends the entire data model and event schema. (CLAUDE.md §5, ARCHITECTURE-SPINE AD-5/6/7)
- (constraint) Identity delegated to Keycloak (self-hosted): SGART stores no credentials and references people only by an opaque id taken from the JWT, never from request body/path. (PRD FR-3, ARCHITECTURE-SPINE)
- (constraint) Architecture paradigm is fixed and binding: DDD + CQRS + Event Sourcing, hexagonal, in a modular monolith; state changes only via command->aggregate->event under optimistic concurrency; read models are projection-only. Full contract in ARCHITECTURE-SPINE.md (adopted companion). Bends every backend design decision.
- (constraint) Clean Code + ubiquitous language: no abbreviations in names; names reflect purpose; one term one meaning (glossary is binding); TDD with domain-first fast unit tests, synthetic data only. Full rules in CLAUDE.md (adopted companion).
- (constraint) Mobile-first: iOS + Android via Flutter/BLoC. Web exists only as an invite-acceptance fallback in v1, not a daily client. (PRD §6)
- (constraint) MVP audience is a curated friends-&-family cohort; no public self-signup. Solo (household-of-one) is a fully-supported first-class case, not an edge case. (PRD §2, §5)
- (decision) NON-GOALS: not a budgeting/personal-finance app; not a retailer/merchant platform and no public/shared price database (price data is private per household); not a pantry/barcode inventory tracker; not a meal planner/recipe app; no social feed/discovery/public list sharing; no full web client in v1; no ads/monetization in MVP; no public self-signup in MVP. (PRD §5)
- (decision) NON-GOALS (out of THIS build - Post-MVP/dropped, reserved for coherence only): receipts & OCR; price intelligence, product pinning, price-based routing; analytics dashboard; configurable notification settings & receipt-scanned notifications; offline presence/delivery-status/automatic-or-field-level merge; geolocation store discovery; additional UI languages & per-market StoreChain data; list duplicate/template (fast-follow); trip pause/resume (DROPPED - lifecycle is Active->Done, cross-day handled by leftover transfer). (PRD §6.2)
- (decision) SUCCESS SIGNAL: real households (solo and multi-person) from the friends-&-family cohort adopt SGART as their actual shopping tool - >=60% complete at least one real weekly Trip for 4 consecutive weeks; and among multi-person households, in >=50% of active household-weeks >=2 distinct Members edit the same list within 24h (live collaboration is the differentiator, not a checkbox). (PRD SM-1, SM-2)

- (decision) CAP-5 REVISED (Timo, 2026-08-22, during epics story creation): off-trip Item actions no longer include check/uncheck/postpone. Rationale: "Done" = bought must carry a Store/Trip context (needed for Post-MVP price observations), and every real journey checks off via a Trip (Ben in-trip; Anna analog still completes a Trip). Off-trip on an Open List = add/edit/remove + **move an Item to another (existing/new) List** (pure reorganization, Item stays Open). Check/uncheck (→Done/Open) and **Postpone** are now Trip-only (CAP-9/CAP-10). Renamed CAP-5 "Item management & off-trip list organization". glossary.md updated: Item Status clarified (Done/Postponed only via a Trip; off-trip always Open), Postpone noted as Trip-time, new term "Move to List" added (distinct from Postpone & Reroute). Reflected in epics.md FR5 + Story 2.4 ("Move an item to another list").
